# Codebase polish — 2026-08-11

An automated elegance/DRY/observability pass over this repo, run via the `codebase-polish` skill. Applies fixes directly rather than only reporting them.

## What ran

1. A live best-practices sweep (the `advisor` skill), refreshed for today — confirmed the existing hybrid design (deterministic tool + LLM judgment, fix-don't-suppress) is still current; no new tool or practice displaces `fallow` for this TypeScript/Node repo.
2. `fallow` (deterministic dead-code, duplication, and complexity scan).
3. Three parallel review lenses: Elegance/Architecture/DRY, Dead-code & duplication triage, Observability & monitoring.
4. Auto-apply, batched to avoid file conflicts, followed by a regression safety net (full test suite, build, lint, format check, plus an independent bug-focused review of the diff).

## Before / after (fallow)

| Metric | Before | After |
|---|---|---|
| Total deterministic issues | 1 | 0 |
| Duplication | 0% | 0% |
| `runPipeline` complexity | critical (cyclomatic 48, cognitive 54) | moderate (cyclomatic 23, cognitive 23), split across 3 functions |
| Functions above threshold | 4 | 6 (the split created 2 new, individually-moderate functions from 1 critical one — a net improvement, see below) |

The function count going from 4 to 6 looks like it moved the wrong way, but it isn't: `runPipeline` was one function scoring *critical* on every metric. Splitting it into `resolvePhases`, `emitPhaseOutput`, and a slimmer `runPipeline` produced three functions that each score only *moderate*. No function in the repo is *critical* anymore. Further splitting would fragment logic that's already close to its natural complexity floor (a 3-boolean decision table, in `resolvePhases`'s case), which the standards brief's own guidance ("not perfect, but better than the current state") argues against chasing.

## Applied — Elegance, Architecture & DRY (opus lens)

- **[MUST]** `run-pipeline.ts`: extracted `resolvePhases()` (pure phase-selection) and `emitPhaseOutput()` (output emission) out of `runPipeline`, cutting it from 137 lines / cyclomatic 48 to three focused functions.
- **[MUST]** `run-pipeline.ts` + `index.ts`: log-file closing was duplicated across 4 exit paths and re-implemented via a pointless dynamic import in `index.ts`; a fire-and-forget `void writeLogLine` could lose the crash line before `process.exit`. Now a single `try/catch/finally` in `runPipeline` closes the log exactly once, and writes are `await`ed.
- **[SHOULD]** Hoisted the duplicated dual-sink logging pattern (stderr + log file, 7 call sites across 4 files) into one `log(verbose, message)` helper in `utils/logger.ts`.
- **[SHOULD]** `reporter/sections.ts`: `pushStaleIndexesSection` had a dead `data` parameter — deleted.
- **[SHOULD]** Consolidated the `--scan`/`--scan-only` alias to a single normalization point in `index.ts`; `run-pipeline.ts`'s `PipelineOptions` no longer carries a redundant `scan` field.
- **[SHOULD]** `reporter.ts` + `reporter/sections.ts`: moved `---` separator emission out of the section builders into `generateReport`, which owns document ordering — verified byte-for-byte identical output.
- **[SHOULD]** Deleted dead code: `readFileContent` (superseded by `readFileContentSafe`), `CLAUDE_ENV_KEY`/`OPENAI_ENV_KEY` (unreferenced, duplicated the live `PROVIDER_ENV` map).
- **[SHOULD]** Deleted the unused `PipelineOptions.apply` field and a speculative "Enact phase (future)" design comment in `run-pipeline.ts`. The actual `--apply` CLI flag and its exit(2) guard in `index.ts` are untouched — that's the real reserved mechanism, documented in `CLAUDE.md`.
- **[NIT]** `scanner.ts`: replaced two hand-rolled index loops in `scanVault` with one `for...of .entries()` loop.
- **[NIT]** `CLAUDE.md`: fixed a stale claim that `run-pipeline.ts` had no unit-test coverage (it does, via `tests/pipeline-phase.test.ts`); noted the `resolvePhases`/`emitPhaseOutput` split.

- Confirmed fallow's zero-duplication, zero-dead-code report by hand-reading all ~20 source files for logic-level duplication a syntactic tool can't see (found the same DRY/dead-code items the architecture lens flagged above — no additional findings beyond those).

## Applied — Observability & monitoring (sonnet lens)

This repo runs unattended on a schedule (launchd, daily 6am) — a silent failure there means nobody finds out until the vault has been silently degrading for weeks. All of the following were confirmed real by tracing actual catch blocks and error paths:

- **[MUST]** `ai-providers/claude.ts`: `completeClaude`'s catch was bare (`catch { return null; }`) — zero signal on the *default* AI provider's failures (auth, rate-limit, network). Now logs the error.
- **[MUST]** `config.ts`: `loadConfig`'s catch silently fell back to placeholder defaults on any error, including a corrupt config file. Now logs non-missing-file errors to stderr before falling back (see the regression-fix note below for a follow-up correction to this).
- **[MUST]** `scripts/setup-launchd.ts`: the generated plist never passed `--log-dir` — the new run-log facility this session added was dead on the one execution path (unattended scheduled runs) it matters most for. Now passes `--log-dir ~/Library/Logs/vault-maintenance`.
- **[MUST]** `fs-helpers.ts` / `scanner.ts`: `readFileContentSafe` silently drops a file that fails to read, with no signal anywhere. `scanVault` now logs a warning naming the file when this happens.
- **[SHOULD]** `ai-suggester.ts`: `parseSuggestions` silently swallowed malformed-JSON errors from the AI response. Now logs before returning `[]`.
- **[SHOULD]** `reporter.ts`: `writeReport`'s `readdir(...).catch(() => [])` treated every error the same as "no same-day reports yet" (masking real I/O/permission errors, since `mkdir` already ran first). Now logs anything unexpected.

## Escalated — not auto-applied

Two findings touch functions the repo's own `CLAUDE.md` documents as `resolver.ts`'s **"Public API"** (`getBrokenLinks`, `getAmbiguousLinks`, `getLinksByStatus`) — real, only-used-by-tests duplication of the single-pass `getBrokenAndAmbiguousLinks`, but deleting a documented public API surface is exactly what this skill's escalation rule reserves for a human decision, not an auto-apply. Proposal: reimplement the two-pass helpers in terms of the single-pass one, or drop them and retarget `tests/resolver.test.ts` at `getBrokenAndAmbiguousLinks` directly, then update the `CLAUDE.md` API line.

## Skipped — genuinely subjective, or not worth the coordination cost

- **`src/index.ts` → `src/cli.ts` rename** (naming lens finding): "index" currently means four different things across this small tree (CLI entry point, the Index.md checker, a barrel module, scanner lookup Maps). Renaming the entry point would also touch `package.json`'s `bin` field and the generated launchd plist's path. Low value relative to that blast radius — skipped.
- **`fs-helpers.ts` cohesion** (moving `formatError`/`isValidDate`/`toISODateString` out, since they're not filesystem-related): a real but purely stylistic organization call, and doing it safely would have required touching 3+ files already being edited by other agents in the same batch. Skipped to avoid merge risk for a NIT-level finding.

## Regression safety net

Full test suite (85 tests), `tsc` build, `eslint`, and `prettier --check` all pass. Also ran `prettier --write` across the whole repo — `.prettierrc` was added to the repo earlier this session but never applied repo-wide, so 26 of 28 source/test files had pre-existing formatting drift unrelated to this polish pass; now consistent.

An independent, empirically-verified adversarial review of the full diff (rendering report output across 7 data shapes, and running 11 CLI scenarios including a mid-pipeline crash with logging active) found 2 real regressions this pass's own edits introduced, plus 1 pre-existing bug it surfaced along the way. All three are fixed:

1. **Regression**: consolidating `ai-suggester.ts`'s "AI suggestions skipped/failed" messages into the new `log(verbose, message)` helper accidentally gated them behind `--verbose` — previously they printed to stderr unconditionally. Fixed: these two messages now write to stderr unconditionally again (matching the original behavior) while still writing to the log file when logging is active.
2. **Regression**: `config.ts`'s new "failed to load config" warning fired even for the completely normal case of no config file being present (the documented default-to-defaults path), which would print daily noise on every scheduled run for any install without a config file. Fixed: the warning now only fires for genuine errors (malformed JSON, permission denied, etc.), not a missing file.
3. **Pre-existing bug, found during the regression check, fixed since it directly concerns `config.ts`**: the `--config <path>` CLI flag never actually worked — commander stored it as `opts.config`, but `runPipeline` read `opts.configPath`, which nothing set. Fixed in `index.ts`.

One accepted tradeoff, not fixed: `ai-suggester.ts`'s `parseSuggestions` is a synchronous function and its new log call can't be awaited, so it can't participate in the `log()` helper's race-safety guarantee (write completes before process exit). Making `parseSuggestions` async purely for this would ripple into its "exported for unit tests" call sites for a low-severity, low-likelihood race (a log line lost on a JSON-parse failure at the exact moment of process exit) — judged not worth the blast radius.
